# 77Photo V1 决策记录

本文件记录拆分计划 T01 对产品设计中留有选择空间的事项所作的决定。实现、前端和运维文档都以这些决定为准；变更时应补充新的决策记录，而不是静默改变接口语义。

## D-001：V1 范围

- 图库和时间线使用同一 `GET /api/v1/photos` 入口，文件夹是唯一的相册模型。
- V1 不实现收藏、虚拟相册、地图、匿名外链分享、全文搜索、AI、人脸识别、在线编辑、后台自动备份、分片上传或视频转码。
- 批量上传属于 V1；批量移动和批量删除属于 V2。
- 视频只保存原文件并返回媒体类型；浏览器支持的格式可用原生播放器播放。服务端不转码，但使用 ffmpeg 为视频和动态照片生成可重建的 WebP poster。

## D-002：媒体格式

- 基本图像验收格式为 JPEG（`image/jpeg`）、PNG（`image/png`）、HEIC（`image/heic`）和 HEIF（`image/heif`）。扩展名、声明 MIME 和实际内容都必须匹配，不能只相信客户端提交的 MIME。
- 接受 `video/mp4`、`video/webm` 以及作为动态照片 companion 的 QuickTime MOV；原文件不变地保存。Web/API 通过 `/api/v1/photos/live-upload` 将 still 与 MOV 作为一个逻辑上传。
- JPEG 中的 MVIMG 尾随 ISO-BMFF 段和 HEIC/HEIF 内嵌视频只在字节边界及 ffprobe 校验通过后提取；派生 motion artifact 可删除并重建，原图永不改写。
- RAW、GIF 和其他未知格式仍返回 `415 UNSUPPORTED_MEDIA_TYPE`，不会留下可见索引或临时文件。
- JPEG/PNG 的尺寸、方向和常用 EXIF 在入库时读取；原图永远不被改写。

## D-003：删除与用户生命周期

- V1 使用永久删除，不实现回收站。删除照片或空文件夹前端必须二次确认；API 删除成功后原文件和索引均不可通过 77Photo 恢复。
- 非空文件夹删除返回 `409 FOLDER_NOT_EMPTY`，不能隐式递归删除。
- 删除用户默认撤销账号和会话，保留其照片文件与索引，并保留一个标记 `deleted_at` 的用户墓碑记录作为不可变 owner 引用；墓碑账号不能登录或出现在可选成员列表中，管理员可在之后转移其照片。也可以在请求中选择 `photo_action=transfer`，此时必须指定现有有效用户作为目标。这样删除默认不会丢失照片，也不会产生孤儿外键。
- 删除或禁用最后一个有效管理员被拒绝。禁用用户会立即撤销其所有会话，但不会删除照片。

## D-004：路径与存储边界

- 客户端只能提交服务端生成的用户 ID、文件夹 ID 和照片 ID，不能提交服务器绝对路径或 `storage_path`。
- 私人根为 `/photos/users/{immutable-user-id}`，共享目录为 `/photos/shared/{folder-id}`；真实路径由服务端生成。
- 所有文件读写先通过 ACL，再进行受限根解析和符号链接逃逸检查。绝对路径、`..`、NUL、控制字符、路径分隔符和保留名称会被拒绝。

## D-005：共享继承与权限

- 文件夹共享记录作用于整个子树；后代文件夹和照片继承最近的祖先共享权限。
- 继承的 `read` 允许列出文件夹、读取元数据、缩略图、预览和原图；禁止上传、移动、重命名、删除和修改共享。
- 继承的 `write` 包含 `read`，并允许在共享目录内上传、移动和重命名照片以及创建、重命名、移动和删除其有权操作的子文件夹。仍禁止把资源移出共享根、修改共享记录或操作共享根之外的资源。
- 共享目录所有者和管理员拥有完整管理权限。普通成员（包括 `write` 成员）不能添加、提升、撤销成员。
- 管理员可读取和修改所有资源，不依赖 `shares` 记录；管理员访问会在响应中标记为 `admin` 来源，便于审计。

## D-006：时间、排序与游标

- 所有 API 时间戳使用带 `Z` 的 RFC 3339 UTC 字符串。客户端提交 `from`/`to` 时必须包含时区偏移，服务端转换为 UTC 后查询；不带时区返回 `400 INVALID_TIMESTAMP`。
- `captured_at` 优先使用 EXIF 拍摄时间；没有可解析 EXIF 时使用文件修改时间。响应同时提供 `captured_at_source`（`exif` 或 `file_mtime`）。
- 图库默认按 `captured_at DESC, id DESC` 稳定排序；相同拍摄时间不会因分页发生重复或遗漏。
- `cursor` 是服务端签名的 base64url 不透明值，绑定用户、筛选条件和排序方向，有效期 15 分钟。客户端不得解析或修改；过期返回 `410 CURSOR_EXPIRED`，筛选条件不一致返回 `400 CURSOR_MISMATCH`。
- `limit` 默认 50，允许 1–100；服务端可能返回少于请求数量。下一页由响应的 `next_cursor` 驱动，不使用 offset。

## D-007：文件名、重复和移动

- 文件名按 Unicode NFC 规范化，去除首尾空白；不能为空、`.`、`..`，不能包含 `/`、`\\`、NUL、控制字符或平台保留名称，长度上限 255 个字节。
- 同一文件夹内重名不会覆盖现有文件。未提供 `conflict` 时返回 `409 NAME_CONFLICT`；`conflict=rename` 由服务端生成稳定后缀（例如 `photo (1).jpg`）。
- 同一文件夹上传的内容 checksum 重复时返回 `409 DUPLICATE_PHOTO`，响应包含已存在的照片 ID；客户端可选择跳过。不会跨用户自动去重。
- 移动先校验源和目标权限，再执行同文件系统原子重命名；跨文件系统时使用安全复制、同步、校验、删除源的补偿流程。索引更新失败会标记待扫描而不会覆盖目标文件。

## D-008：上传事务与限制

- 上传使用流式 multipart 请求，单文件大小由 `PHOTO_MAX_UPLOAD_SIZE` 限制，超过限制返回 `413 UPLOAD_TOO_LARGE`。
- 文件写入同一数据文件系统的临时文件，完成 checksum/元数据读取后 `fsync` 并原子重命名，再写入索引。任一步失败都会删除临时文件并隐藏索引记录。
- 客户端断开、磁盘写满、无效图片、像素数超过解码上限或数据库写入失败都返回错误，不产生可见半文件；管理员 rescan 可发现并修复已落盘但未入库的文件。

## D-009：首次初始化与认证

- 服务第一次启动且没有用户时，必须通过本地绑定的 `POST /api/v1/setup/admin` 创建首个管理员；该接口只在数据库为空时可用，成功后永久关闭。
- 初始化和登录都使用 Argon2id 哈希与每用户独立 salt。登录失败统一返回 `401 INVALID_CREDENTIALS`，不区分用户名不存在、密码错误或账号禁用。
- Session 存在服务端数据库，可撤销；浏览器使用 HttpOnly、Secure（生产）、SameSite=Lax Cookie。所有 Cookie 写请求要求 `X-CSRF-Token` 与会话 token 匹配。

## D-010：扫描状态

- 只有管理员可触发手动扫描；同一时间最多一个扫描任务，重复触发返回现有任务的 `409 RESCAN_ALREADY_RUNNING`。
- `POST /api/v1/admin/rescan` 返回 `202` 和任务 ID；`GET /api/v1/admin/rescan/{jobId}` 返回 `queued`、`running`、`completed` 或 `failed` 以及新增、更新、缺失、失败计数。
- 扫描无法完整访问存储根时不会批量把文件标记为缺失；扫描会记录失败并保留原索引。扫描排除缓存、临时文件和回收站路径，并拒绝符号链接逃逸。

## D-011：管理员访问范围

- 管理员可以管理用户、触发扫描、读取和修改所有照片/文件夹，并可管理任意共享记录。
- 管理员不能通过 API 读取密码哈希、Session token 或其他认证秘密；日志同样禁止记录这些值。
