# M5 视频自动备份开发记录（未发布）

2026-09-29 至 30 当前实现：照片备份设置新增默认关闭的视频开关；Android 13+ 分别申请图片和视频权限，Android 14+ 对选定媒体授权给出单独提示；Android 12 使用媒体读取权限。原生扫描按图片、视频分别保留游标，指纹包含集合、卷、MediaStore 版本、ID、大小和修改时间。旧照片指纹在扫描时迁移，不重新上传已确认文件。目标目录切换时保存各自的完成历史。

MP4、WebM 通过原有上传接口发送，其他格式显示未完成。界面显示照片和视频的确认数量、当前上传百分比、失败原因及各自最近完整扫描时间。网络及可恢复服务端错误按媒体种类退避；服务器拒收的大小或格式错误等待用户重新尝试。暂存前检查可用空间，仍保持单个暂存文件。备份键使用服务器身份和不可变账号 ID；旧用户名键先隔离旧完成历史；旧记录中的目录所有者 ID 与服务器当前所有者 ID 均为当前账号时才采纳。共享或已转移目录重新扫描并由服务器按内容去重；同名新账号不会抢占旧账号的迁移机会。

应用内“开始可见视频传输”由用户主动发起 Android `dataSync` 前台服务，通知提供暂停和取消，Android 15+ 的服务超时保存待继续状态。原生端保存当前视频指纹及通知动作；即使进程在 JS 记录状态前被回收，下次扫描仍能恢复暂停或取消。可见传输的客户端期限为 5 小时；服务端仅对已认证的普通上传请求把读写期限延长至 6 小时，其他接口仍使用原有 30/60 秒期限。自动任务把超过 128 MB 的视频留给用户发起可见传输；传输前先持久化当前指纹，有限窗口内被中断后不在每次后台任务重复暂存或上传。Wi-Fi 条件在传输中变化时会取消当前请求。目标目录删除或失去写入权限时，备份在暂存前暂停，等待用户重新选择目录或主动重试。服务器磁盘或配额耗尽返回 507 STORAGE_FULL，客户端显示可理解的原因。

本地检查：`npm test -- --runInBand`（当前 64 个测试）、`npm run typecheck`、`npm run lint`、`go test ./...`；`ANDROID_HOME=/home/ubuntu/Android/Sdk ./gradlew :app:compileDebugKotlin -PreactNativeArchitectures=arm64-v8a --offline --quiet` 通过。ARM64 APK 构建在 `:app:configureCMakeDebug[arm64-v8a]` 停止：本机 Android SDK 的 `cmake` 缺少宿主机 `libdl.so.2`，因此这里无法完成原生 APK 构建验证。以上检查不证明前台服务通知、实机权限和传输行为。M5.5 的最终原生承载决策须在 ARM64 真机原型验证后写入 `docs/DECISIONS.md`。

待完成：ARM64 真机上验证前台服务类型、通知权限、暂停/取消及 Android 15+ 时限；受限网络下超过旧 120 秒限制的真实视频和实际代理超时验证；Android 12、13、14+ ARM64 实机权限、后台与重启联调；目标目录撤权、磁盘满、令牌刷新、多地址切换、原视频哈希和资源峰值验收。上述验收通过前，M5 不应标记完成或发布。
