# M3 基础搜索开发记录（草稿）

日期：2026-09-29。范围：服务端照片列表、Web 图库、查询契约和索引。工作树同时包含尚未提交的 M2 改动；本记录仅说明 M3。

## 查询约定

- `GET /api/v1/photos` 支持 `q`（去除两端空白后最多 100 个 Unicode 字符）和 `media_type=photo|video`，可组合原有 `folder_id`、`from`、`to`。纯空白 `q` 等同普通列表；控制字符 NUL、CR、LF 与非法媒体类型返回 400。
- 文件名为字面量包含匹配，`%`、`_` 无通配含义；ASCII 字母不区分大小写，其他字符按原样匹配。动态照片以主照片记录归入 photo，独立视频归入 video。
- 排序保持 `captured_at DESC, id DESC`。签名游标绑定全部筛选条件。查询和续页存在性检查均使用可见性、未回收站和索引完成状态条件。
- Web 顶部搜索入口打开并聚焦图库文件名输入框。日期输入表示用户本地日历日，开始日零点包含、结束日次日零点不包含；转换为带 `Z` 时区的时间戳发送。条件写入图库 URL 与会话状态。

## 1 万 / 10 万条性能复核

环境：Linux aarch64，4 vCPU Neoverse-N1，23 GiB RAM，Go 1.24.13，SQLite（modernc）。`PHOTO_SEARCH_PERF=1 go test ./internal/photos -run '^TestSearchPerformance$' -count=1 -v` 生成确定性数据：一半位于共享文件夹，一半位于私有文件夹；约 20% 为视频，约 4.3% 文件名含 `family-trip`。每种查询预热一次，以下为随后一次服务层 `List` 调用的耗时和 Go `TotalAlloc` 增量，返回上限 50 条；磁盘缓存已预热。管理员和仅有共享文件夹读取权的成员分别测量。数值为本机样本，不代表目标服务器延迟。

“调整前”是在同一索引和数据生成器下，临时去掉列表 SQL 的 `INDEXED BY photos_active_timeline_idx` 后测量；调整后为当前代码。调整前 SQLite 选择 `photos_scan_status_idx` 并为排序建临时 B 树。调整后使用 `photos_active_timeline_idx`，日期场景在 `captured_at` 上做范围查找，其他场景按时间线扫描；成员场景继续执行共享 ACL 子查询。文件名包含匹配不会使用普通文件名 B 树索引。

AND captured_at<?)`，均不再有临时排序。共享成员仍有 `CORRELATED SCALAR SUBQUERY`，文件夹筛选仍有递归 descendants 查询。新的部分索引只包含 `deleted_at IS NULL AND scan_status='indexed'` 的行。无筛选浏览在这一数据集没有回退。
