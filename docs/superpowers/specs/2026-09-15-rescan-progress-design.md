# 重新扫描进度显示设计

## 背景

管理员点击“重新扫描文件”后，当前页面只显示“扫描已排队”，无法知道任务是否仍在运行、已经处理了多少文件，或最终是否成功。后端已经提供了 `GET /api/v1/admin/rescan/{jobId}`，返回任务状态和扫描计数，因此只需要补齐前端状态查询与展示。

## 目标

- 启动扫描后显示持续更新的扫描状态。
- 显示已扫描、新增、更新、缺失和失败数量。
- 扫描进行中禁用“重新扫描”按钮，避免重复任务返回 409。
- 扫描完成后保留最终统计；扫描失败时显示失败状态。
- 中英文界面使用现有 i18n 机制。
- 不为了计算百分比额外遍历文件系统；扫描进行中使用不定长进度条，完成时显示 100%。

## 非目标

- 不修改后端扫描算法和任务生命周期。
- 不增加持久化任务历史；刷新页面后不恢复之前的扫描任务。
- 不显示虚假的百分比。后端没有可靠的待处理文件总数，扫描中只展示活动状态和计数。

## 方案

### API 客户端

在 `ApiClient` 增加 `getRescan(id)`，调用现有的 `GET /api/v1/admin/rescan/{jobId}`，并定义复用的扫描任务类型，包含 `id`、`status`、`counts`、完成时间和错误信息。

`startRescan()` 成功后，设置当前任务 ID，并立即查询一次任务状态；随后用串行定时查询继续更新，避免上一次请求尚未返回时产生重叠请求。任务进入 `completed` 或 `failed` 后停止定时器。

### 设置页状态

设置页保存当前任务快照和轮询计时器的清理逻辑。组件卸载或任务结束时清理定时器；如果请求在组件卸载后返回，不再更新 React 状态。

启动接口失败仍显示“无法开始扫描”。启动成功后的任务失败显示“扫描失败”，并保留后端返回的最终计数。轮询期间的单次网络错误不立即丢弃任务，下一次定时查询继续尝试；任务状态仍可见。

### 界面

图库索引区域保留现有标题和按钮，在下方增加状态区域：

- `queued` / `running`：显示动态不定长进度条、当前状态和五项实时计数。
- `completed`：进度条填满，显示完成状态和最终计数。
- `failed`：显示失败状态和最终计数，按钮恢复可用。

扫描中按钮禁用，任务完成或失败后恢复可用。进度区域使用现有的浅色布局和 `progress-track` 样式，不新增卡片或复杂装饰；进度条补充可访问名称和当前状态文本。

## 数据流

```text
点击重新扫描
  -> POST /api/v1/admin/rescan
  -> 保存 job.id，显示 queued
  -> GET /api/v1/admin/rescan/{jobId}（串行定时查询）
  -> 更新 status 和 counts
  -> completed/failed 后停止查询并恢复按钮
```

## 测试

- API 客户端测试：验证扫描任务状态接口路径、返回数据解析以及启动后任务查询所需的类型。
- 设置页测试：验证启动后显示排队/运行状态和计数，完成后显示最终状态并恢复按钮，失败状态也能停止轮询。
- 保留现有 Go、前端单元测试、类型检查和生产构建作为回归验证。

## 验收标准

1. 管理员点击一次后按钮立即禁用，页面显示扫描状态和动态进度条。
2. 扫描运行期间，计数随后端状态查询更新。
3. 扫描完成时进度条为 100%，显示最终五项统计，按钮恢复可用。
4. 扫描失败时显示失败状态和最终统计，按钮恢复可用。
5. 非管理员与现有权限行为不变；未引入额外文件系统遍历。
